# Логика работы приложения (диалог пользователя и нейродруга)

Документ описывает **фактическое поведение backend** на момент написания: как из входящей реплики пользователя получается ответ нейродруга, что влияет на тон, когда возможна исходящая реплика без пользователя и как учитываются границы и романтическая динамика. Для деталей кода см. файлы в скобках.

---

## 1. Три способа «появиться» реплике нейродруга

| Сценарий | Триггер | Где в коде |
|----------|---------|------------|
| **Ответ на текст** | `POST .../messages` | `conversations.py` → `affect_lite` → `generate_reply` |
| **Ответ на голос** | `POST .../perception/audio` (после STT, если прошёл wake/addressing) | `perception.py` → тот же пайплайн + TTS |
| **Инициатива** | Фоновый sweep / воркер, когда пользователь **не писал** достаточно долго и выполнены условия готовности | `initiative_runner.py` → `generate_initiative_ping` |

Текст и голос проходят **один и тот же смысловой контур**: обновление состояния → генерация ответа LLM → запись в чат и события.

## 2. Конвейер одной пользовательской реплики (текст или голос после транскрипта)

Упрощённая последовательность:

1. **Голос (дополнительно):** Whisper → проверки guard’ов → при необходимости **wake**: если речь не считается обращённой к нейродругу, ответ **не генерируется** (`reply_text` пустой, событие `voice_message_ignored`). См. `perception.py`.
2. **`touch_relationship`** — обновляется `last_interaction_at` у основной связи `user_main`.
3. **`snapshot_after_user_text`** (`affect_lite.py`):
   - лёгкая эвристика **настроения** по ключевым словам (например «спасибо», «люблю» → чуть выше valence/attachment; «злой», «бесит», «стоп» → ниже valence, выше hurt);
   - **`apply_boundary_to_state`** — по тексту вычисляются **трение**, **режим границы**, флаги для снимка состояния;
   - если включён **`romantic_dynamics_enabled`**, вызывается **`update_affection_after_event`** (архетип, границы, эвристика + опционально LLM-hint романтики) → обновляются scores в `RelationshipModel` и поля affection / romantic interest / intimacy в новом снимке;
   - в БД сохраняется новый **`InternalStateSnapshot`**.
4. **`update_relationship_boundaries`** — по тому же тексту корректируются долгоживущие поля связи: `conflict_memory_score`, `boundary_safety_score`, `repair_receptivity`, `respect_baseline` и т.д. (`boundary_response_service.py`).
5. Логируется входящее событие (`text_message_in` / `voice_message_in`).
6. Собирается контекст для LLM:
   - **`build_recent_transcript_text`** — последние реплики активного треда (до ~24 сообщений, обрезка по символам);
   - **`retrieve_snippets`** — фрагменты семантической памяти + при включённой настройке SQL-память;
   - **биография** — снимок для системного промпта;
   - для голоса — **`speaker_context`** (кто говорит), если включён `voice_addressing_enabled`.
7. **`generate_reply`** (`llm_orchestrator.py`) — один вызов Chat Completions: system = личность + состояние + границы + романтический контекст + память + транскрипт; user = текст пользователя.
8. Ответ пишется в чат и логируется как исходящее событие; для голоса дополнительно **TTS** (см. §7 про скорость).

**Важно:** финальные формулировки ответа задаёт **языковая модель**. Числовые поля и режимы (`boundary_mode`, `bond_type`, valence, hurt…) **не берутся как жёсткая программа реплики**, а **подмешиваются в system prompt**, чтобы сместить стиль.

## 3. Как определяется, *что* сказать и в каком тоне

### 3.1. Личность и стиль (персона)

В системный промпт попадают:

- имя, **архетип**, gender-style;
- **ядро черт** и **правила речи** из `IdentityCore`;
- при наличии — **`character_voice`** и **`life_legend`** (жёстче задают отличимый голос);
- **биография** и **профиль экспертизы** (сильные/слабые темы);
- блок **`DIALOGUE_NATURALNESS_RU`**: меньше «опросника», не заканчивать каждую реплику вопросом, можно мягко возражать, без шаблонной лести и «службы поддержки».

Уровень уверенности по теме: **`get_expertise_level(user_text, expertise_profile)`** → в промпт добавляется строка вида «тема классифицирована как … — подстрой уверенность».

Итог: **тон и содержание** — это в основном **инструкции к LLM + пресет**, а не отдельный rule-engine для каждой фразы.

### 3.2. Числовое «настроение» как подсказка модели

В `generate_reply` в system добавляется строка с **последним снимком**:

`valence`, `attachment`, `loneliness`, `hurt`, `friction`, `boundary_alert`.

И строка про **отношение**: `trust`, `warmth`, `attachment` из `RelationshipModel`.

Это не означает «обязательно обидеться»: модель видит приближённые метрики и интерпретирует их вместе с текстом пользователя.

### 3.3. Границы и «холод», обида, пауза

Отдельного модуля «нейродруг обиделся и молчит» в ответ на сообщение **нет**: каждый раз при входящем тексте вызывается генерация ответа (если не отсечён голосовой wake).

Зато есть **явная лексическая оценка грубости** и накопление **трения**:

**Уровни неуважения (`evaluate_disrespect_level`):**

- уровень **3**: слова вроде оскорблений, «отвали», «ненавижу тебя» и т.п. (`INSULT_WORDS`);
- уровень **2**: «бесишь», «молчи», «надоел» и т.п.;
- уровень **1**: восклицательная интонация в сочетании со «стоп» / «хватит» / «не хочу».

**Ремонт диалога:** слова вроде «извини», «прости», «давай нормально» → **`repair_signal`**, трение частично снижается.

**Режим границы (`select_boundary_mode`):**

| Режим | Условия (упрощённо) |
|--------|---------------------|
| `normal` | низкое трение, нет сильного disrespect |
| `dry_distance` | лёгкое трение или disrespect 1 |
| `clear_boundary` | disrespect 2 или трение выше порога |
| `cooldown` | disrespect 3 или очень высокое трение |
| `repair_opening` | есть сигнал извинения |

В промпт через **`boundary_prompt_context`** попадают **английские** инструкции: при `dry_distance` — короче и меньше тепла; при `clear_boundary` — ясно обозначить границу; при `cooldown` — короткий отказ от грубого тона, охлаждение, без оскорблений в ответ.

Параллельно из disrespect повышаются **`hurt`**, снижаются **`valence`** и **`safety`** в рамках одного шага (`apply_boundary_to_state`).

**Инициатива после конфликта:** прямой флаг `initiative_cooldown` из snapshot в раннер инициативы **не подключён**. Зато **`get_boundary_cooldown_factor`** снижает готовность к исходящей инициативе, если у связи высокий **`conflict_memory_score`** или низкий **`boundary_safety_score`** — см. §6.

### 3.4. Романтика и тип связи (Stage C)

При включённом `romantic_dynamics_enabled`:

1. **Эвристика** по тексту: маркеры тепла и романтики (`evaluate_warmth_signal`, `evaluate_romantic_signal`).
2. Опционально (**по умолчанию включено**): **`romantic_signal_llm_hint`** — короткий JSON «intensity» 0..1; итоговый романтический сигнал = **max(эвристика, hint)**. Без API-ключа шаг пропускается.
3. **`boundary_check`** может **заблокировать** усиление романтики/флирта при конфликте, высоком трении, режимах `cooldown` / `clear_boundary` и порогах по полям связи.
4. Обновляются **`affection_score`**, **`emotional_intimacy_score`**, **`romantic_tension_score`** с **ограничением шага за одно сообщение** (нет скачка в «романтику за один чих»).
5. Пересчитывается **`bond_type`**: `platonic`, `warm_acquaintance`, `warm_friendship`, `emotional_close`, `romantic_soft` — по порогам близости и напряжения с учётом блокировки романтики.

В **`romantic_prompt_context`** в system попадают **русские** указания тона по типу связи (дружеский / тёплый без форса / бережная близость / осторожная романтическая окраска) и напоминание не обгонять уровень связи.

### 3.5. Голос: просодия TTS

При **`stage_c_tts_prosody_enabled`** и включённой романтической динамике скорость синтеза **`tts_speed_for_bond_type`**: чуть медленнее при более тёплой связи (`romantic_soft` ~ 0.93 относительно ~1.02 для platonic). Это влияет на **звучание**, не на текст ответа.

## 4. Когда нейродруг пишет первым (инициатива)

Инициатива — это **отдельный сценарий**: пользователь **ещё не отправлял** сообщение в этой «волне».

**Условия «можно попробовать отправить»** (`build_initiative_status` + `try_send_initiative`):

- **`initiative_enabled`** (глобальный флаг);
- есть время последнего **входящего** от пользователя (`text_message_in` / `voice_message_in`); от него считается **`gap_hours`**;
- не **тихие часы** для часового пояса пользователя (`initiative_quiet_hours_*` интерпретируются как локальное время в выбранном timezone);
- **`readiness_score`** ≥ **`initiative_readiness_threshold`**  
  - score растёт от gap между `initiative_gap_hours_min` и `initiative_gap_hours_strong`, умножается на **теплоту** связи и обнуляется в quiet hours;
  - затем умножается на **`boundary_cooldown_factor`** (конфликтная связь → инициатива реже или не доходит до порога);
- с момента последнего **`initiative_message_out`** прошло не меньше **`initiative_cooldown_hours`**.

Если всё выполнено, вызывается **`generate_initiative_ping`**: тот же каркас личности + транскрипт + состояние + границы + романтический контекст + память, плюс явная инструкция: пауза **`gap_hours`**, писать **коротко**, без упреков за молчание, чаще без вопроса в конце.

Запуск массовой проверки: internal **`POST .../initiative/sweep`** и/или `scripts/initiative_worker.py` (см. документацию инфраструктуры).

## 5. Память и недавний диалог

- **Транскрипт чата** — не источник истины для доменной логики, но **подаётся в LLM** как «недавний диалог», чтобы ответ был связным.
- **Семантическая память:** запрос по тексту пользователя (и для инициативы — фиксированный размытый запрос про настроение). При включении — дополнительно SQL `memory_items`.

---

## 6. Fallback без LLM или при ошибке API

- Нет клиента OpenAI или ошибка / пустой ответ:
  - **`generate_reply`**: запасная русская фраза вида «Слышу. Про „…“ — откликаюсь…»;
  - **`generate_intro_message`** / **`generate_initiative_ping`**: короткие шаблонные тексты.
- Это важно для тестов и для диагностики: если в проде видите только fallback — проверьте ключ и логи.

## 7. Соответствие ожиданиям и пробелы

**Что система делает хорошо для продукта:**

- Единый пайплайн текста и голоса.
- Явные пороги для грубости и «охлаждения» тона через промпт + долговременные scores конфликта для инициативы.
- Плавное наращивание «романтического слоя» и тип связи с ограничителями за ход.

**Чего нет или это упрощено (не стоит ожидать из текущего кода):**

- Нет отдельной FSM «обиделся → N минут молчит»: ответ генерируется на каждое принятое сообщение.
- Флаг **`boundary_response_enabled`** в конфиге **нигде не отключает** цепочку границ — фактически логика границ всегда активна в `affect_lite`.
- **`initiative_cooldown`** из оценки границы за сообщение **не блокирует** sweep напрямую; подавление инициативы идёт через **conflict_memory / boundary_safety** и общий cooldown между исходящими инициативами.
- Решение «что именно сказать» в тонкостях остаётся за **LLM**; числа — мягкое руление, не детерминированный сценарий.

При изменении ожидаемого поведения имеет смысл править либо **промпты и пороги** в перечисленных сервисах, либо вводить явные политики (например жёсткий отказ ответа при режиме X), если понадобится 100% предсказуемость.

## 8. Addendum v4.4 — tracked events и repair initiative

Реализация по `docs/SRS/NeuroFriend_Addendum_v4_4_Repair_And_Tracked_Events (1).md` (упрощённый MVP без отдельной сущности `ConflictEpisode`).

### 8.1. Отслеживаемые события

- После логирования входящего **текста/голоса** вызывается **`ingest_from_user_message`**: при **`TRACKED_EVENTS_ENABLED`** и наличии API выполняется **LLM JSON** — список кандидатов с типами (`birthday`, `flight`, `deadline`, `promise`, …), признаками `needs_clarification` и пропусками полей.
- В БД создаются строки **`tracked_events`** (часто в статусе `draft`).
- В **`generate_reply`** в system добавляется **`tracked_events_context`**: черновики с недостающими полями и ближайшие **подтверждённые** события (если включено **`EVENT_CLARIFICATION_ENABLED`** для блока уточнений).
- Подтверждение и время события — через API (**`PATCH .../tracked-events/{id}`** → `status=confirmed`) или создание вручную (**`POST`**); при подтверждении с датой и **`TRACKED_EVENT_REMINDERS_ENABLED`** создаются строки **`tracked_event_reminders`**.

### 8.2. Инициатива: напоминание → repair → обычная

Общий **`initiative_cooldown_hours`** применяется ко **всем** исходящим типам подряд.

1. **Event follow-up:** если есть просроченное **`tracked_event_reminders`** (pending, `remind_at <= now`, событие `confirmed`), генерируется **`generate_event_followup_ping`**, событие лога **`event_followup_initiative_out`**, `message_kind=event_followup`.
2. **Repair:** если у связи **`unresolved_conflict`**, прошла пауза и порог **`repair_readiness`** (см. `repair_initiative_service`), отправляется **`generate_repair_ping`**, лог **`repair_initiative_out`**, увеличивается **`repair_attempt_count`**.
3. Иначе — прежняя **обычная инициатива** (`initiative_message_out`).

**Флаги конфликта:** при грубой реплике / режимах границы `sync_relationship_conflict_flags` выставляет **`unresolved_conflict`** и **`last_conflict_at`**; слова примирения (**«прости»** и т.д.) снимают флаг и поднимают **`repair_success_rate`**.

### 8.3. Поля состояния

На каждом **`InternalStateSnapshot`** сохраняются **`conflict_peak`**, **`cooldown_active`**, **`repair_readiness`**, **`reconnection_need`** (для промптов и отладки). Решение об исходящей repair-инициативе на sweep дополнительно использует **`compute_repair_readiness_now`** по текущему времени.

### 8.4. API отладки

- **`GET /v1/neurofriends/{id}/conflicts/active`**
- **`GET|POST|PATCH .../tracked-events`**, **`POST .../complete`**, **`POST .../reminders`**
